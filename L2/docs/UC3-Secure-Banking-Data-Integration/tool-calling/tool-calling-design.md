# Tool-Calling Integration Module — Design Notes

Deliverable: "Tool-calling integration module," per L2 HLD UseCase3.

## How this connects to L2/UC2's RagAssistant

L2/UC2's `RagAssistant` answers policy questions by retrieving from documents. It has no access to — and must never fabricate — live account data. L2/UC3's `BankingToolService` is the complementary half: it answers live-data questions by calling real backend logic, and never goes through an LLM at all. `IntentClassifier` is the router between them:

```
User query
    │
    ▼
IntentClassifier.classify(query)
    │
    ├── POLICY_QUESTION ──────────► RagAssistant.ask(query)         (L2/UC2 — retrieval + guarded generation)
    ├── ACCOUNT_BALANCE ──────────► BankingToolService.getAccountBalance(token, customerId)
    ├── TRANSACTION_HISTORY ──────► BankingToolService.getTransactionHistory(token, customerId, accountNumber, limit)
    ├── LOAN_OUTSTANDING ─────────► BankingToolService.getLoanOutstanding(token, customerId)
    └── AMBIGUOUS ────────────────► (a real orchestrating agent would ask a clarifying question or split into multiple tool calls; out of this use case's scope)
```

This is the concrete mechanism satisfying L2 HLD UseCase3's Business Context: "This information must be retrieved securely and not generated by the AI model." A live-data query is routed to `BankingToolService` **before** any prompt is built or any LLM is invoked — there is no code path in this submission where an LLM sees a live-data question and is asked to answer it directly.

## Why this is "tool calling," not a manually-written if/else in a controller

The four `BankingToolService` public methods (`getAccountBalance`, `getTransactionHistory`, `getLoanOutstanding`, plus `IntentClassifier` as the selector) are written as callable, self-describing tools specifically so a real LLM-orchestrated agent (e.g., using OpenAI/Anthropic function-calling, or LangChain4j's tool-calling support) could invoke them directly once a real LLM API is reachable — each method's parameters and return shape are already a clean tool signature:

```java
// Tool: get_account_balance
List<MaskedAccount> getAccountBalance(String bearerToken, String requestedCustomerId)

// Tool: get_transaction_history
List<MaskedTransaction> getTransactionHistory(String bearerToken, String requestedCustomerId, String accountNumber, int limit)

// Tool: get_loan_outstanding
List<MaskedLoan> getLoanOutstanding(String bearerToken, String requestedCustomerId)
```

In this sandbox, `IntentClassifier`'s keyword-based router plays the role a real LLM's function-calling decision would play (same disclosed-heuristic approach as L2/UC2's guardrails, for the same reason: no reachable LLM API here). The swap-in path is: replace `IntentClassifier.classify()`'s call site with an LLM call that receives the tool signatures above as its available-functions list and decides which (if any) to invoke — the tool methods themselves would not need to change at all.

## Security boundary this design enforces

Because tool selection and tool execution are separate steps, and execution never depends on what the (real or stubbed) LLM "said," a compromised or hallucinating classification step can at worst call the *wrong* tool (e.g., mis-route a policy question to `getAccountBalance`, which would then correctly fail because the classifier doesn't have a `customerId`/token context to call it with) — it cannot make a tool *return fabricated data*, because every tool's data always comes from `BankingDataStore` and is always subject to `BankingToolService.verifyAndAuthorize`'s real JWT check, regardless of how the tool was selected.

## What this module deliberately does NOT include

Multi-turn conversation state, clarifying-question generation for `AMBIGUOUS` intents, and function-calling wire-format adapters (OpenAI's `tools` schema, Anthropic's `tool_use` blocks) are out of this use case's scope — L2 HLD UseCase3 asks for the tool-calling *integration module* (the callable tools + the routing decision), not a full conversational agent loop, which is closer to L2/UC5's "Final Integrated Banking RAG System" scope.
