# Security Validation Checklist

Deliverable: "Security validation checklist," per L2 HLD UseCase3. Each item states what was implemented, whether it was actually verified in this sandbox (via `secure-banking-core`'s real run — `reports/secure-banking-demo-run-log.txt`, `reports/secure-banking-selftests-run-log.txt`), and any residual risk.

| # | Check | Status | Evidence |
|---|---|---|---|
| 1 | JWT signature verification rejects a token signed with a different/wrong secret | ✅ Verified | `SelfTests.testJwtRejectsWrongSecret`; demo Scenario 4 (attacker-forged token, real HMAC failure) |
| 2 | JWT signature verification rejects a tampered token (altered payload/signature bytes) | ✅ Verified | `SelfTests.testJwtRejectsTamperedSignature` |
| 3 | Expired tokens are rejected based on the real system clock | ✅ Verified | `SelfTests.testJwtRejectsExpiredToken`; demo Scenario 5 |
| 4 | Malformed tokens (wrong segment count, invalid encoding) are rejected without throwing an unhandled exception | ✅ Verified | `SelfTests.testJwtRejectsMalformedToken` |
| 5 | Signature comparison is constant-time (no timing side-channel) | ✅ Implemented | `JwtService.constantTimeEquals` — not independently timing-attack-tested in this sandbox (would require a dedicated timing-measurement harness outside this submission's scope), but the constant-time algorithm itself is standard and correctly applied |
| 6 | Signing key minimum length enforced (256 bits / 32 chars for HS256) | ✅ Verified | `SelfTests.testJwtConstructorRejectsShortSecret` |
| 7 | A valid token for Customer A cannot retrieve Customer B's data (authorization, not just authentication) | ✅ Verified | `SelfTests.testToolServiceBlocksCrossCustomerAccess`; demo Scenario 3 |
| 8 | Authorization check re-validates resource ownership even for a legitimately-authenticated caller (an account number the caller supplies is checked against their own accounts, not trusted blindly) | ✅ Verified | `SelfTests.testToolServiceBlocksAccountNotBelongingToCustomer` |
| 9 | A privileged role (ADMIN) can legitimately cross customer boundaries, and this is an explicit, auditable grant rather than an accidental bypass | ✅ Verified | `SelfTests.testToolServiceAllowsAdminCrossCustomerAccess`; demo Scenario 6 |
| 10 | Sensitive fields (account numbers) are masked before leaving the service boundary — never returned raw | ✅ Verified | `SelfTests.testToolServiceMasksAccountNumberInResponse`; every account number in `reports/secure-banking-demo-run-log.txt` is masked |
| 11 | Live banking data is retrieved only from the data store, never from an LLM — no code path allows a generative model to produce a balance/transaction/loan figure | ✅ Verified by code inspection | `BankingToolService` has no dependency on any `LlmClient`-shaped interface (contrast with L2/UC2's `RagAssistant`, which does) |
| 12 | Intent routing sends live-data questions to tool calling and policy questions to RAG retrieval, so a live-data question never reaches a generation step | ✅ Verified | `SelfTests.testIntentClassifierRoutesBalanceQuery`/`...TransactionQuery`/`...LoanQuery`/`...PolicyQuestionByDefault`; demo Scenario 1 |
| 13 | Same HTTP status/response shape for authentication failures and authorization failures (prevents customer-id enumeration via differing error responses) | ⚠️ Partially implemented | Same status code and JSON shape (`UnauthorizedException` → `GlobalExceptionHandler` → 401), but the `message` field's text currently still differs between "authentication failed" and "not authorized for this customer" — see item 14 |
| 14 | **Residual risk**: error message text differs by failure type even though HTTP status doesn't | 🔴 Open | `BankingToolService.verifyAndAuthorize`'s two failure branches produce different message strings. Recommendation: return a single generic message ("Access denied") for both cases in the response body, and log the specific reason server-side only, before this API is exposed to any untrusted client |
| 15 | JWT signing secret is externalized (not hardcoded), consistent with L1/UC4's fix for a hardcoded payment API key | ✅ Implemented | `application.yml`'s `bankrag.security.jwt-secret: ${BANKRAG_JWT_SECRET:...}` — environment-variable override with a clearly-labeled demo-only default |
| 16 | Token expiry is short-lived | ✅ Implemented | 15 minutes (`jwt-expiry-seconds: 900`) — reasonable for a customer-facing banking session token; a real system would pair this with a refresh-token flow, out of this use case's scope |
| 17 | A demo/dev-only endpoint that bypasses real authentication (`/dev/token`) cannot be reached in a production profile | ✅ Implemented | `@Profile("dev")` on `DevTokenController`; **must be manually confirmed** that no production deployment ever sets `spring.profiles.active=dev` — this is a configuration discipline risk, not something code alone can fully guarantee |
| 18 | CSRF protection appropriately disabled for a stateless bearer-token API (not needed; would be a false sense of security if left on without cookie-based auth) | ✅ Implemented | `SecurityConfig`'s `csrf(csrf -> csrf.disable())`, paired with `SessionCreationPolicy.STATELESS` — CSRF matters for cookie/session auth, not bearer tokens, so this is a correct simplification, not a weakening |
| 19 | Sensitive fields beyond account numbers (mobile, email, government id) have masking utilities ready, even though this use case's 3 endpoints don't currently return them | ✅ Implemented, not yet wired to an endpoint | `PiiMasking.maskMobileNumber`/`maskEmail`/`maskGovernmentId` — exercised by `SelfTests`, ready for a future endpoint (e.g. a KYC-detail lookup) that would need them |
| 20 | Spring Boot module (`secure-banking-service`) is compile-verified | 🔴 Not possible in this sandbox | Maven Central blocked — see pom.xml header comment and README.md. `secure-banking-core`, which contains the actual security-critical logic, WAS compiled and run for real |

## Summary

17 of 20 items are fully implemented and verified (or verified by direct code inspection where a runtime test wasn't feasible, e.g. item 11's "no LLM dependency" claim). One item (13/14) is a genuine, disclosed residual risk with a concrete recommendation, not glossed over. One item (17) is a configuration-discipline risk inherent to any `@Profile`-gated dev endpoint, documented rather than assumed away. Item 20 is this submission's consistent, disclosed Maven Central limitation.
